# Инцидент 2026-09-10 — ransomware-вайп БД

Бот зашёл снаружи на открытый `bind-address = *` :3306 со старым паролем `savetube_user` и дропнул все таблицы `savetube_db`, оставив ноту RECOVER_YOUR_DATA с требованием выкупа. Не платить: «бэкап» у таких ботов — блеф, данные они не хранят.

## Лечение (выполнено)

- Пароль `savetube_user` сменён (актуальный — в серверном `/var/www/save-tube/data/savetube/.env`, там же `MYSQL_HOST=127.0.0.1`).
- `bind-address = 127.0.0.1` в `/etc/mysql/mysql.conf.d/mysqld.cnf` + `systemctl restart mysql`. Наружу не открывать.
- Юзеров `%` в `mysql.user` быть не должно (проверка: `SELECT user,host FROM mysql.user;`).
- Реквизиты из утечшего `.env` (GitHub-секрет `ENV_FILE` и т.п.) считать скомпрометированными при повторении.

## Восстановление (flashback из binlog)

На сервере `log_bin=ON`, ретенция binlog 7 дней — это позволило откатить вайп без дампа:

1. `mysqlbinlog -v --base64-output=DECODE-ROWS` по файлам до момента DROP.
2. Реигр row-образов: INSERT/UPDATE/**DELETE** — DELETE обязателен, иначе воскрешаются отвязанные пользователями карты.
3. Заливка через `INSERT IGNORE`.

Позиционные схемы удалённых таблиц (порядок колонок в row-событиях):

- payments: `(id, merchant, status, email, created_unix, untiled_dt, rate, amount, title, provider, method)`
- recurrent_subscriptions: `(id, email, rate, method_id, card_type, last4, active, next_billing, created, streak)`
- app_users: `(uuid, email, password_hash, created)`

Особенности:

- Email плательщиков из API ЮKassa НЕ достать (чеки внешние, `/v3/receipts` пуст) — email восстанавливался из binlog.
- Парсинг больших binlog на VPS — только стримингово и под `nice`; буферизация вывода в память = OOM (на VPS 3.7 ГБ RAM).
- Часть премиумов восстановлена синтезированными строками payments с title «(восстановление)» — у них нет merchant_id, это норма.

Итог восстановления: 95 автопродлений, 182 платежа yookassa, 81 юзер, премиум у 102 юзеров. T-Bank-платежи без дат в историю не возвращались (решение владельца).
